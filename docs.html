Connect a model

Open Settings from the top right of the main window, then choose API on the left.

A Cloud API needs three things: a key, a base URL, and a model name. After you fill them in, test the connection. Create the key in that provider’s own console. The cloud / local control next to the input chooses which one this turn uses.

There are two local paths. On an Apple silicon Mac, MLX downloads and loads a model inside the app. llama.cpp needs you to start the local service yourself, then connect from the app. The app does not start that outside process for you.

A cloud model sends that turn to the provider you configured. The key stays on this Mac and is not written into the chat. Local model weights are not uploaded.

Settings

The left side has six pages:

  • API: a cloud or local model.
  • Agent: the working folder, whether writing is allowed, and developer mode. Code & Write uses this when it changes files and runs programs.
  • Mail: the mailbox connection and today’s inbox.
  • Work Brief: who you are, and what to keep in mind at work.
  • App: language, reminders, appearance, opening this guide again, and erasing local usage data.
  • iCloud sync: sign in, upload by hand, load by hand, and a local backup.

The assistant control at the top right of the main window opens the Work Brief directly.

If Agent settings still shows an automatic calendar window, that window checks what is due. It is not a fourth chat mode.

Work Brief

“Who I am” is identity and routine. That original text is for you. “Consider at work” is what scheduling and tasks must respect.

Completing the brief compares what you already wrote with the recent conversation, appends facts you have said, and asks a few short questions for the rest. After you save and generate the summary, later turns read three short summaries. They do not paste the whole original into every turn.

Constraints you write in the current chat, such as “don’t”, “must”, “only use”, are carried into the next turn. This is not a personal archive that grows on its own.

The first task

After a model is connected, stay in Ask & Do. Type “basketball at 9 in the morning.” A confirmation card appears in the chat first. The calendar changes only after you agree.

To write several items at once, wait until the reply already contains the plan, then use the to-do list. To add one item yourself, without the model, use Add on the main window.

Code & Write and Multi-agent wait until the local runner is installed. Installation asks you to confirm.

Ask & Do

Ask & Do is for chat, public lookup, and putting something on the calendar.

When you mention a specific time, a calendar confirmation card appears first. It is written only after you confirm. Hold to talk, and the text enters the field when you let go. Pictures, Word, PDF, and Excel can be attached to the same message.

With the web on, an answer searches public pages first. With it off, the reply uses only what the model already knows.

When you name a plugin that is installed and enabled, the call leaves from this same chat, and the result comes back here.

Code & Write

Choose a folder first. Files are written in that directory.

It writes, runs, and brings the result back. The chat shows the command and the exit status. If the program writes a result file, the chat gives you that file.

The first time, install the local runner. Installation asks you to confirm. After developer mode is on, allowed programs can run in the working folder. The app does not run install scripts on its own, and it does not open an unrestricted terminal.

Code & Write is not another IDE window. It stays in the same app as Ask & Do and Multi-agent.

Multi-agent

The built-in roles are Control, Engineer, Reviewer. You can also make a custom role from an existing one. The app writes a role card. Future feature will support add your agent to a team.

Multi-agent team work in a form of workflow. And, we've uploaded three pre-set coding workflows, and will upload one video workflow. Users can complete specific through according workflow.

These roles are not people. They do not sign, pay, or send contracts. This mode also waits until the local runner is installed.

Plugins

On the plugin page you can search, install, enable, and fill in an account. Installation asks you to confirm. The chat does not download a plugin by itself.

Say the plugin’s name in Ask & Do, Code & Write, or Multi-agent. All three use the same call.

If it is not installed, the chat tells you to install it on the plugin page. If it is disabled, enable it there first. If it needs an account, fill that in on the plugin page. The password goes to the Keychain and does not appear in the chat.

The reply is a console card: what was called, the exit status, and the output. A long reply scrolls inside the card. Listing tools is not a real call. After you say what to record or look up, you see that tool’s result.

Version 2.19 adds MCP control of external plugins, so the app can extend what it does. A plugin from the catalog still has to be installed and enabled before it runs.

Calendar

You can switch between the calendar view and the list. An item the model suggests appears as a confirmation card first. It is written only after you agree.

Add on the main window does not go through the model. Use it to add one item yourself. The record page shows to-dos, history, and counts.

Skills

A skill is a file of steps, not a plugin. You can put one in three places:

  • ~/.agents/skills
  • .agents/skills in the current folder
  • ~/AgentButler/skills

The app reads one of them when the task matches. These are steps you wrote. They are not habits learned from every file on the Mac.

Web

The globe on the composer decides whether this turn may use the web. Off means the reply uses only what the model already knows. On means the app searches first, reads the pages it needs, then answers.

Paper lookups go through arXiv. The query does not include a local path or a secret.

Mail

The mail page in Settings has two parts. Gmail and Outlook use Nylas: the full address, that provider’s app password, and a Nylas v3 API key. iCloud uses IMAP on this Mac: name@icloud.com plus an Apple app-specific password.

Today’s inbox lists the sender and a short summary. The model can draft a reply. It sends only after you edit it and agree. The app does not take over the whole mailbox.

Where data stays

A plugin secret stays in the Keychain and is handed to that plugin only while it runs. The chat and this guide do not show the secret.

Before a reply, the app picks a limited set from this conversation: what was said, pages used this time, commands that ran, files involved, and constraints you wrote. A short follow-up such as “this” or “continue” also keeps the last few lines. There is a cap. There is no vector index, and no second model scoring those lines.

Calendar events live in the system calendar. A plugin’s own database stays in that plugin’s folder. Skill files are instructions you placed there. None of those three is the excerpt taken from the chat.

A cloud model provider may keep the request under its own policy. That belongs in the provider’s notice, not as storage by this app.

Erase local usage data is in App settings. It clears usage on this Mac. It does not delete iCloud, and it does not sign you out. It cannot be undone.

Sync and backup

Open Settings, then iCloud sync. Signing in with Apple only signs you in. Upload to iCloud and load from iCloud are each another tap. Sync writes to the iCloud account signed in on this Mac right now.

These do not upload: API keys, local model weights, and files in the working folder you chose.

The same page can export a .butlerpack, for another computer or for when you do not want to sign in with Apple. The backup has the Work Brief, window memory, calendar, and chats. It does not have secrets or model files. Restoring a backup replaces the brief on this Mac, and it asks again before it does.

Say it. It finishes the work on your Mac.
